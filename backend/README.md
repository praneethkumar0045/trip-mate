# TripMate AI Backend

This folder contains the FastAPI backend for TripMate AI. It turns a free-text travel request into a draft travel plan by running a LangGraph workflow, collecting available research, validating the draft, and pausing for human review before finalizing it.

This document describes the backend as it currently exists in the repository. It also records implementation gaps so a future upgrade does not mistake planned or partial behavior for working functionality.

## Current capabilities

- Accepts a travel request as natural language.
- Extracts origin, destination, trip duration, dates, traveler count, and budget using a Groq-hosted chat model.
- Routes through flight, hotel, location, and weather research steps.
- Generates a day-by-day itinerary and checks it with deterministic checks plus an LLM validator.
- Pauses after a passing validation and supports a human approve/revise decision.
- Returns a user-facing plan, validation failure, or human-review response through a versioned REST API.

Suggestions and research are not bookings. In particular, hotel output is currently generated by an LLM and is not backed by an availability or booking provider.

## Architecture and request flow

The ASGI application is `app.main:app`. It mounts the version-one router at `/api/v1`.

The travel workflow in `app/graph/graph.py` currently runs in this order:

1. **Travel request extraction** — `travel_request` asks the configured LLM for JSON and validates it against the Pydantic travel-request schema.
2. **Supervisor routing** — the supervisor node itself does not call an LLM. `app/graph/routing.py` selects the first incomplete research step in this fixed order: flight, hotel, location, weather, then itinerary.
3. **Research**:
   - **Flights** — AviationStack, but only after mapping a supported origin and destination to IATA codes and receiving a departure date.
   - **Hotels** — an LLM-generated requirements/suggestions report; no hotel provider is called.
   - **Location** — geocodes the destination with OpenStreetMap Nominatim.
   - **Weather** — gets a daily Open-Meteo forecast using the geocoded coordinates.
4. **Itinerary generation** — the LLM drafts an itinerary from the request and collected results.
5. **Validation** — deterministic checks require a destination, positive integer duration, non-empty itinerary, and day headings matching the requested duration. A second LLM check evaluates consistency and evidence grounding.
6. **Human review** — a passing itinerary interrupts the graph. The caller can approve it or request a revision with feedback.
7. **Final response** — after approval, another LLM formats the user-facing response. Some flight, hotel, and weather status text is then enforced in application code.

The workflow allows up to two validation attempts. The current graph configuration has a routing defect on the exhausted-validation path; see [Known gaps and upgrade priorities](#known-gaps-and-upgrade-priorities).

## Requirements and configuration

- Python with syntax support for Python 3.10 or newer. The pinned dependencies and your target deployment runtime should also be checked for compatibility before upgrading.
- The dependencies in `requirements.txt`.
- A Groq API key.
- A SQLAlchemy-compatible database URL. The project includes PostgreSQL's Psycopg driver; PostgreSQL is the expected database setup.
- An AviationStack API key for live flight searches. This setting is optional at application startup, but flight research reports an error when it is not configured.
- Network access to Groq, AviationStack (if enabled), Nominatim, and Open-Meteo.

Create `backend/.env` (do not commit it or paste its secret values into prompts):

```dotenv
APP_NAME=TripMate AI
APP_VERSION=1.0.0
DEBUG=true
DATABASE_URL=postgresql+psycopg://DB_USER@DB_HOST:5432/DB_NAME
GROQ_API_KEY=your_groq_api_key
AVIATIONSTACK_API_KEY=your_aviationstack_api_key
```

`DATABASE_URL` and `GROQ_API_KEY` are required settings. `AVIATIONSTACK_API_KEY` is optional. Replace the database placeholders with your database connection details; if credentials are included in the URL, URL-encode reserved characters. The settings loader reads `.env` relative to the process's current working directory, so run the commands below from `backend/`. Environment variables can also supply these values. Unknown settings are ignored.

The chat model is currently fixed in `app/llm/factory.py` to `qwen/qwen3.8-27b`, with temperature `0`. Changing the model currently requires a code change; it is not configured through an environment variable.

## Run locally

From the repository root in PowerShell:

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload
```

If PowerShell prevents activation, use the virtual environment's executable directly:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

The API is then available at `http://127.0.0.1:8000`. Interactive API documentation is at `/docs`; the alternative documentation is at `/redoc`, and the OpenAPI schema is at `/openapi.json`.

The application currently does not create database tables at startup, and the travel API does not read or write the SQLAlchemy models. The graph uses an in-memory checkpointer instead. Consequently, a database URL is required by settings, but configuring a database does not currently make travel sessions durable.

## HTTP API

All application routes are under `/api/v1`.

### `GET /api/v1/health`

Returns a basic process-level health response:

```json
{
  "status": "ok",
  "service": "TripMate AI"
}
```

This endpoint does not check database connectivity, LLM credentials, or external providers.

### `POST /api/v1/travel`

Request body:

```json
{
  "query": "Plan a 5 day trip from Hyderabad to Goa"
}
```

`query` is required and must contain at least three characters. Successful request parsing and graph execution can return one of these workflow-level statuses:

- **`human_review_required`** — includes `thread_id`, the draft `travel_plan`, and a `review` object with `type`, `message`, and `validation`. Use the thread ID to submit the review.
- **`success`** — includes the final `travel_plan`, `completed_agents`, and `missing_details` (`travel_dates`, `travelers`, and `budget`).
- **`validation_failed`** — intended to return a failure `message`, `validation` result, and no travel plan when validation is exhausted. The graph routing defect noted below can prevent this response from being reached.

Every response includes `query` and `thread_id` where `build_response` is used. Workflow statuses are JSON response fields, not HTTP status codes. Invalid request bodies are handled by FastAPI/Pydantic (normally HTTP 422); an unhandled workflow failure is returned as HTTP 500.

Example with `curl.exe` in PowerShell:

```powershell
curl.exe -X POST "http://127.0.0.1:8000/api/v1/travel" `
  -H "Content-Type: application/json" `
  -d '{\"query\":\"Plan a 5 day trip from Hyderabad to Goa\"}'
```

### `POST /api/v1/travel/{thread_id}/review`

Resume a graph paused for human review. The request model is:

```json
{
  "approved": true,
  "feedback": ""
}
```

`approved` is required; `feedback` defaults to an empty string. Set `approved` to `false` and include revision guidance in `feedback` to request changes. The response uses the same workflow response shape as the initial travel endpoint. A revision may be validated and paused for review again.

The current graph checkpointer is process-local memory. A review must reach the same running application process that owns the paused thread; a process restart loses the checkpoint. There is no user identity or authorization check on either endpoint.

## Data storage and migrations

SQLAlchemy defines these models in `app/db/models.py`:

- `User`: unique email and creation timestamp.
- `Conversation`: belongs to a user and can have messages.
- `Message`: belongs to a conversation and stores role, content, and creation timestamp.

`app/db/session.py` creates a synchronous SQLAlchemy engine from `DATABASE_URL` and exposes a session dependency. `app/db/init_db.py` offers a `create_all` helper, but it is not invoked by `app.main` or the travel API.

Alembic is configured by `alembic.ini` and `alembic/env.py`. The only checked-in revision is currently a no-op (`upgrade()` and `downgrade()` contain `pass`). Do not treat it as a schema-creating migration or assume the database schema is current. Before relying on persistence, design and test real migrations, then wire storage into the application.

## Integrations and current limitations

| Capability | Current implementation | Important limits |
|---|---|---|
| LLM | `ChatGroq` from `langchain-groq`; model fixed as `qwen/qwen3.8-27b` | Requires `GROQ_API_KEY`; outputs and availability depend on the external provider. |
| Flight search | AviationStack `/v1/flights` endpoint | Requires an API key for results. The agent currently maps only Hyderabad (`HYD`) and Goa (`GOI`). It needs a departure date and a supported origin/destination; no booking is performed. |
| Hotel research | LLM prompt that identifies requirements and missing information | No hotel search API, verified listings, prices, availability, or reservations. |
| Geocoding | OpenStreetMap Nominatim search endpoint | One search result is requested; dependent on network and Nominatim service/policy. |
| Weather | Open-Meteo forecast endpoint | Forecast horizon is limited to 1–16 days. Dates are forecast dates and are not automatically proven to match the requested travel dates. |
| Workflow checkpoint | LangGraph `MemorySaver` | In-memory only; not shared across workers and lost on process restart. |
| Database | SQLAlchemy models and Psycopg dependency | Not used by current travel request/review endpoints; current Alembic revision is empty. |

Research failures may be represented as unavailable/error results so the workflow can still draft a plan, but the plan should not be described as confirmed travel inventory. The prompts explicitly distinguish grounded research from general recommendations; continue preserving this distinction when upgrading providers or response schemas.

## Testing and verification

The repository currently has standalone scripts under `scripts/`, not a configured pytest suite. Run commands from `backend/` after installing dependencies and setting the required environment variables:

```powershell
python scripts/test_validation_failure.py
python scripts/test_graph_validation_failure.py
```

These exercise validation routing/failure behavior; `test_graph_validation_failure.py` builds a small test graph with mocked nodes.

Other scripts make real model or provider calls and may incur cost, require API credentials, or fail due to network/provider availability:

```powershell
python scripts/test_graph.py
python scripts/test_flight_api.py
python scripts/test_weather_api.py
python scripts/test_weather_agent.py
python scripts/test_weather.py
```

`test_weather.py` and `test_weather_agent.py` are manual agent checks; the latter's supplied state omits location coordinates, so weather may be reported unavailable. There is no project-level automated test command configured in the backend at present. Avoid treating successful imports or the health endpoint as proof that an end-to-end travel plan, review resume, provider call, or database migration works.

## Known gaps and upgrade priorities

These are observations from the current implementation, not assumed roadmap commitments:

1. **Fix and test exhausted validation routing.** `route_after_validation()` can return `"validation_failed"` when attempts are exhausted, but the corresponding conditional-edge mapping in `build_graph()` includes only `"itinerary"` and `"human_review"`. The production graph therefore does not route that branch to the existing `validation_failed` node, unlike the separately assembled graph in `scripts/test_graph_validation_failure.py`.
2. **Persist workflow state.** Replace or augment `MemorySaver` with a durable LangGraph checkpointer and define thread ownership, expiration, and behavior across multiple workers/restarts.
3. **Connect persistence deliberately.** The database models and session helper are unused by the travel API. Define what users, conversations, messages, and generated plans mean, add real Alembic migrations, and then wire transactions and lifecycle rules into the API.
4. **Replace hotel text generation with a data provider** if verified hotel availability, rates, links, or booking actions are product requirements. Until then, expose it as unverified suggestions.
5. **Generalize flight location resolution.** Replace the hard-coded two-city airport map with validated IATA resolution and define behavior for unsupported destinations, round trips, multi-city requests, and dates.
6. **Harden API operations.** Add authentication/authorization, request limits, CORS policy if a browser frontend needs cross-origin access, structured logging, correlation IDs, provider timeouts/retries, and rate/cost controls as appropriate. Current API has no auth or CORS configuration; exceptions are printed and returned as generic 500 errors.
7. **Improve asynchronous execution and error handling.** Some workflow nodes call synchronous LLM methods or `asyncio.run`; review these under the graph's async execution model and make provider failures observable and consistently represented.
8. **Formalize contracts and tests.** Add API and graph tests for success, invalid input, missing dates, unsupported locations, provider errors, validator retries, validation-failure routing, approval, revision, and checkpoint expiry/restart. Keep the client-facing response schema stable and documented.
9. **Review deployment configuration.** `DEBUG` defaults to `true`; set safe production defaults, validate required settings at startup, and provide a deployment/runtime strategy for secrets, database connections, and multiple workers.

Suggested upgrade order: fix the validation routing bug; establish a repeatable automated baseline; decide persistence and session semantics; then evolve provider coverage and public API contracts with tests and migration/versioning strategy.
